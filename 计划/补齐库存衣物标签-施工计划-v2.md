## 0. AI 速读卡

- 一句话目标：管理员对指定用户的存量衣物分批执行一次 AI 补标，只追加缺失信息，不删除、不替换已有数据。
- 目标用户：管理员；实际被处理者是管理员明确选择的某个用户。
- 核心流程：确认目标用户 -> 小批量分析照片 -> 合并缺失标签 -> 每件独立落库 -> 返回剩余数量和异常清单。
- 关键事实：照片无法保证识别出完整 12 组标签；不确定的标签组会保持为空。
- 完成口径：所有“有照片且尚未成功分析”的衣物都已尝试处理，不代表每件衣物的 12 组标签都非空。
- 最大风险：把“AI 调用成功”误写成“标签全部补齐”，以及请求超时后重复触发同一批。
- P0 验收：不覆盖旧值、不改 garment.category、不串用户、失败可重试、超时不重复处理、刷新后进度仍正确。

## 2. 背景与真实能力边界

指定账号有 100+ 件衣物，很多是在结构化标签库上线前录入的，因此 taxonomyTags 和旧扁平字段可能为空或不一致。

现有 GarmentVisionService.analyzeImage(fileName) 可以读取已存照片并返回经过白名单过滤的识别结果，但必须接受以下事实：

- AI 只会返回照片中能判断的标签。
- 不确定的组会返回空数组，不保证 12 组都有值。
- 未配置 QWEN_API_KEY、图片不存在、网络失败、超时或返回格式异常时，现有服务会返回 confidence=0 的空 fallback。
- 当前 AI 搭配主要读取 seasons、styleTags、sceneTags、color 等扁平字段，因此结构化标签和扁平镜像必须保持一致。

因此，本功能的准确名称应理解为“对存量衣物做一次 AI 最佳努力补标”，不能承诺“自动补满全部标签”。

## 3. 已确定的产品决策

### 3.1 硬约束

1. 不覆盖任何已有标量值。
2. 不删除任何已有数组标签。
3. 数组允许追加 AI 返回且当前不存在的白名单值，绝不整体替换。
4. garment.category 永远不改。
5. taxonomyTags.category 表示细分品类，与 garment.category 不是同一个字段；代码和测试必须区分。
6. 没照片的衣物不调用 AI，不写处理标记，返回完整可查看清单。
7. AI fallback、失败或落库失败不写处理标记，下次可以重试。
8. 有效 AI 响应即使没有新增字段，也可以写处理标记，避免同一照片无限重复调用。
9. 处理标记表示“本轮 AI 已成功分析过”，不表示 12 组标签全部非空。
10. 同一目标用户同一时间只允许一个补标请求运行。

### 3.2 推荐默认

- 每批默认 3 件，服务端最大也为 3 件。
- 单批服务端总时间预算 90 秒。
- 小程序请求 timeout 为 120000 毫秒。
- 按衣物 ID 升序处理，结果稳定、方便核对。
- 每件衣物独立提交，AI 调用放在数据库事务外，落库放在独立事务内。
- 首次正式运行 limit=1；人工确认无误后才使用 limit=3。

### 3.3 本版本不做

- 不改 AI 模型、提示词和标签库。
- 不自动或定时跑全站。
- 不修改 pocket、chestMark 等结构特征。
- 不做多人审批和逐件确认页面。
- 不引入 Redis、队列或新依赖。
- 不保证 AI 能补出照片无法判断的材质、穿着感等信息。
- 不提供“清空所有 AI 标签”的按钮。

## 4. 状态与完成口径

保留新增字段 tagsBackfilledAt，含义固定为：

> 这件衣物已经收到一次有效 AI 响应，并完成了本次安全合并。

状态判断：

| 状态               | 条件                           | 是否写 tagsBackfilledAt | 是否自动重试   |
| ------------------ | ------------------------------ | ----------------------- | -------------- |
| no-photo           | 没有 photo.fileName            | 否                      | 否，转人工清单 |
| pending            | 有照片且 tagsBackfilledAt 为空 | 否                      | 是             |
| analyzed-filled    | 有效响应且写入至少一个值       | 是                      | 否             |
| analyzed-unchanged | 有效响应但没有可追加值         | 是                      | 否             |
| unreadable         | confidence=0 的空 fallback     | 否                      | 是             |
| failed             | AI 之外的代码或数据库错误      | 否                      | 是             |

有效 AI 响应的最低条件：

1. confidence 是有限数字且大于 0。
2. taxonomyTags、seasons、styleTags、sceneTags 的结构符合 GarmentVisionResult 约定。
3. 所有准备写入 taxonomyTags 的值再次经过 sanitizeGarmentTaxonomySelection。

禁止只凭 changed=true 就认定成功。低置信度或畸形结果不得污染数据库。

接口和页面不得再使用“全部标签补完”这样的文案。正确文案：

- “有照片的衣物均已分析”
- “本次分析 X 件，新增标签 Y 项”
- “仍有 Z 件待重试”
- “另有 N 件无照片，需要手动处理”

## 5. 标签合并与镜像一致性

### 5.1 空值定义

- 标量空值：undefined、null、空字符串或纯空格。
- 数组空值：undefined、null、空数组，或清洗后没有有效值。
- “unknown”“other”等合法业务值不是空值，必须保留。

### 5.2 合并顺序

每件衣物按以下顺序生成补丁，不能边判断边直接改实体：

1. 用清洗后的视图判断现有值，但不主动删除历史脏值、未知键或旧格式。
2. 用现有扁平字段补 taxonomyTags 中对应的空组。
3. 用现有 taxonomyTags 补空着的扁平字段。
4. 如果两边都已有值但互相冲突，全部保留，不让 AI 覆盖，并增加 mirrorConflictCount。
5. 最后才把 AI 结果追加到仍可补充的位置。
6. 生成一个纯补丁和变更明细，再在独立事务内应用到实体。

### 5.3 数组规则

taxonomyTags 各分组、seasons、styleTags、sceneTags 都使用“去重并集”：

- 已有：通勤
- AI：通勤、简约
- 保存后：通勤、简约

禁止把整个数组替换为 AI 数组。

### 5.4 标量规则

color、material、thickness、fit、subcategory 仅在当前为空时写入。

若 taxonomyTags 和扁平字段都已有冲突值：

- 不自动修正。
- 不把冲突算作失败。
- 在返回结果中统计 mirrorConflictCount，供人工核对。

### 5.5 字段映射

| taxonomyTags 分组 | 扁平字段    | 规则                                      |
| ----------------- | ----------- | ----------------------------------------- |
| season            | seasons     | 春季/夏季等与 spring/summer 等双向映射    |
| color             | color       | 中文颜色与 GarmentColor 枚举双向映射      |
| style             | styleTags   | 数组去重并集                              |
| occasion          | sceneTags   | 数组去重并集                              |
| material          | material    | 标量只补空                                |
| thickness         | thickness   | 标量只补空                                |
| fit               | fit         | 标量只补空                                |
| category          | subcategory | 只补 subcategory，绝不改 garment.category |

weather、colorFeeling、wearingFeel、length 没有旧扁平镜像，只保存到 taxonomyTags。

映射和清洗规则应放在 GarmentService 或 garment-tag-taxonomy.ts，不在 Controller 和小程序前端重复实现。

**复用约束**：季节中英文映射、中文颜色↔GarmentColor 映射在 `src/ai/garment-vision.service.ts` 已有实现（SEASON_LABEL_TO_VALUE、SEASON_ALIASES、COLOR_LABEL_TO_VALUE、COLOR_VALUE_TO_LABEL）。本任务应复用这些定义，或将其抽取为共享常量后两处引用，**禁止另写一套并行映射**，防止日后改一处漏一处。

## 6. 批次、超时与并发

### 6.1 批次

- BACKFILL_LIMIT_DEFAULT = 3
- BACKFILL_LIMIT_MAX = 3
- limit 必须是 1 至 3 的整数。
- 字符串、数组、对象、NaN、Infinity、0、负数和小数统一返回 400，不静默转换。

现有单图 AI 超时默认 25 秒，但生产可通过 AI_VISION_TIMEOUT_MS 覆盖。服务端必须读取实际配置值，确保：

单批预算 >= 单图超时 × 批次上限 + 15 秒余量，且单批预算小于客户端 timeout。

若生产配置使 3 件无法满足这个公式，就自动把本批上限降到 1 或 2 件，不能继续使用固定的 3 件上限。

若连 1 件也无法满足公式，接口在调用 AI 前返回 503，并提示检查 AI_VISION_TIMEOUT_MS；不得启动一个注定会超过客户端 timeout 的请求。

进入循环前还必须预检 QWEN_API_KEY 非空。缺少 Key 时直接返回 503，不逐件制造 unreadable 结果，也不写任何处理标记。

到达预算时：

- 不再开始下一件。
- 已经成功落库的结果保留。
- 返回 deadlineReached=true 和正确的 remainingUnattempted。

### 6.2 同一用户并发保护

MiniappAdminService 维护按 targetUserId 区分的运行锁：

- 已有请求运行时，新请求返回 409。
- 无论成功、异常还是超时，finally 都必须释放锁。
- 小程序收到 409 时提示“该用户正在补标签，请稍后刷新”。

当前生产为单容器，进程内锁可满足本版本。若未来横向扩容，必须升级为数据库租约，不得继续依赖进程内锁。

### 6.3 每件独立落库

1. AI 调用在事务外执行，避免长时间占用数据库事务。
2. 根据当前最新数据生成补丁。
3. 在单件事务内重新查询并应用补丁。
4. 只 flush 当前衣物。
5. flush 成功后才增加成功计数。
6. flush 失败时回滚并重新加载实体，不能让脏对象影响下一件。
7. remainingUnattempted 必须以数据库最终状态为准，不能只看失败后仍被修改的内存对象。

## 7. 架构分工

### MiniappAdminController

- 接收 targetUserId 和 limit。
- 读取当前 JWT 用户。
- 做入口参数校验：项目无全局 ValidationPipe，class-validator 装饰器不会自动生效，limit 必须在此手动校验；非 1–3 整数一律抛 BadRequestException（400）。
- 调用 MiniappAdminService。
- 不写合并算法、不直接操作数据库。

### MiniappAdminService

- assertAdmin 必须在第一步。
- 校验目标用户存在。
- 管理目标用户运行锁、批次、时间预算和返回统计。
- 调用 GarmentVisionService 分析照片。
- 调用 GarmentService 完成标签合并和单件落库。

### GarmentService

- 负责现有标签标准化。
- 负责 taxonomyTags 与扁平镜像互补。
- 负责只追加、不覆盖的补丁生成。
- 负责单件事务、持久化和变更明细。

### GarmentVisionService

- 继续负责读图、调用 Qwen、返回规范化结果。
- 本任务不修改模型和提示词。

### 架构例外记录

现有架构文档规定普通衣物入库的 AI 结果需要用户确认。本任务属于管理员、指定账号、存量数据的一次性批处理例外。

施工时必须同步 docs/backend-architecture-source-of-truth.md，写清：

- 普通新增/编辑流程仍须用户确认。
- 只有管理员补标接口可以按本计划自动追加空缺值。
- 该接口仍禁止覆盖任何已有值。

## 8. API 契约

### 请求

POST /api/miniapp/admin/users/:id/garments/backfill-tags

```json
{
  "limit": 3
}
```

### 成功响应

```json
{
  "targetUserId": 12,
  "requestedLimit": 3,
  "effectiveLimit": 3,
  "total": 108,
  "withPhoto": 101,
  "attemptedThisRun": 3,
  "analyzedThisRun": 2,
  "filledGarmentCount": 2,
  "filledFieldCount": 11,
  "unchangedCount": 0,
  "unreadableCount": 1,
  "failedCount": 0,
  "mirrorConflictCount": 1,
  "noPhotoCount": 7,
  "remainingUnattempted": 99,
  "completionState": "needs-retry",
  "deadlineReached": false,
  "noPhotoItems": [{ "id": 31, "name": "黑色短袖" }],
  "failedItems": []
}
```

### 错误响应

- 400：limit 不是 1 至 3 的整数。
- 403：当前用户不是管理员。
- 404：目标用户不存在。
- 409：目标用户已有补标请求运行。
- 503：QWEN_API_KEY 缺失，或 AI_VISION_TIMEOUT_MS 无法满足单件请求时间预算。
- 500：批次级错误；不得把密钥、文件绝对路径或数据库 SQL 返回给小程序。

failedItems 只返回可理解的错误分类，例如 image-unreadable、storage-error、database-error，不返回内部堆栈。

当前目标用户预计只有 100+ 件衣物，本版本应返回全部 noPhotoItems。为防止异常大数据量，服务端最多返回 500 条；超过时增加 noPhotoItemsTruncated=true，并明确提示需要分页或导出。页面必须展示或允许复制这份清单，不能只显示数量。

completionState 取值：

- needs-retry：仍有 unreadable 或 failed。
- has-more：本批完成，但仍有未分析衣物。
- photo-complete：有照片衣物均已分析，且没有失败。
- photo-complete-with-no-photo：有照片衣物均已分析，但仍有无照片衣物。

## 9. 小程序交互

管理员库存页标题从“库存导出”调整为“库存管理”。

点击 AI 补标签后先弹确认框，内容至少包含：

- 用户名称和用户 ID。
- 当前衣物总数。
- “只追加空缺，不覆盖原值”。
- “本次最多分析 3 件，可能产生 AI 调用费用”。

- 当前目标用户按钮显示 loading。
- 所有补标按钮暂时禁用，避免误点其他账号。

完成后用结果弹窗显示：

- 本次分析件数。
- 新增标签项数。
- 仍待处理件数。
- 未识别/失败件数。
- 无照片件数和衣物清单。
- 镜像冲突数量。

禁止仅用 wx.showToast 承载完整结果；Toast 只提示“本批完成”。

当 remainingUnattempted=0：

- noPhotoCount=0：显示“所有有照片衣物均已分析”。
- noPhotoCount>0：显示“有照片衣物已分析，另有 N 件无照片待手动处理”。
- 不显示“全部标签补完”。

## 11. 数据库迁移

新增 nullable 字段：

- TypeScript：tagsBackfilledAt?: Date
- PostgreSQL：tags_backfilled_at timestamptz null
- SQLite：tags_backfilled_at datetime null

项目在 AppModule.onModuleInit 中自动执行 migrator.up()，因此：

1. 不能把生产环境当第一次迁移测试。
2. 本地先用临时 SQLite 数据库验证 up、实体读写和 down。
3. PostgreSQL SQL 至少做编译和结构审查；有本地容器时再跑真实 migration up。
4. 部署前备份数据库。
5. 新容器启动日志必须确认迁移成功；迁移失败则停止部署，不继续点补标按钮。

重要：down migration 只会删除 tags_backfilled_at 列，不会撤销已经新增的标签。真正的数据回滚必须依赖部署前数据库备份。
